## Findings

### F-1 [HIGH-INFO, NOT-A-BLOCKER] — RLS bypass in local dev because postgres superuser

**Symptom:** User logged in as `pakbudi` (tenant_id=3) ses query `GET /api/products` returns 16 rows (mix dari tenant 2 + tenant 3). Expected: 8 rows (only tenant 3).

**Root cause:**

- Migration `20260505300000_force_row_level_security` apply `FORCE ROW LEVEL SECURITY` ke semua tabel tenant-scoped.
- Tapi Postgres `FORCE RLS` hanya bypass ke **table owner**, BUKAN ke role dengan `rolbypassrls=t` (superuser, atau role yang explicit di-grant `BYPASSRLS`).
- Local dev pakai `postgres` superuser dari container default — `rolsuper=t`, `rolbypassrls=t`, jadi RLS skip total.
- `SET LOCAL app.current_tenant = '3'` di middleware berhasil, tapi RLS policy never evaluates.

**Verifikasi:**

```sql
-- Run as postgres superuser:
SET app.current_tenant_id = '3';
SELECT count(*) FROM products;
-- → 16 (RLS bypassed)
```

**Production impact:** ZERO. Supabase service_role / anon role tidak ada `BYPASSRLS`, jadi RLS apply normally. Migration comment di `20260505300000` udah explicit:

> "Postgres bypasses RLS for table owners by default; this ensures the policy applies even when the app connects as the schema owner (dev/CI test). Production typically uses a non-owner role (e.g. Supabase service role) which is already subject to RLS without FORCE — so this is purely defense."

Tapi ini gak nutup case `BYPASSRLS=t`.

**Recommendation:**

1. **Optional dev improvement** — add migration / setup script to create a non-superuser app role for local dev:

   ```sql
   CREATE ROLE vipos_app NOLOGIN NOSUPERUSER NOBYPASSRLS;
   GRANT ALL ON SCHEMA public TO vipos_app;
   GRANT ALL ON ALL TABLES IN SCHEMA public TO vipos_app;
   GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO vipos_app;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO vipos_app;
   ```

   Then `DATABASE_URL=postgresql://vipos_app@localhost/vipos`. Ensures local dev validates tenant isolation, mirrors production behavior.

2. **Production deploy checklist** — tambahin di runbook: "Verify the connecting role does NOT have BYPASSRLS=t before deploy". Cek dengan:

   ```sql
   SELECT rolname, rolsuper, rolbypassrls
   FROM pg_roles
   WHERE rolname = current_user;
   ```

   Both `rolsuper` and `rolbypassrls` MUST be `f` for the deploy.

3. **CI test improvement** — current P2-02 RLS tests probably running as superuser too. Consider adding a CI job that uses `vipos_app` (non-superuser) to validate cross-tenant isolation locks down.

**Severity:** HIGH-INFO (deployment hygiene), bukan launch blocker. Production fine. Local dev punya gap visibility.

### F-2 [LOW] — Login response missing `tenant_id` in user object

**Symptom:** `POST /api/auth/login` returns:

```json
{
  "token": "...",
  "user": {
    "id": 3,
    "username": "pakbudi",
    "name": "Pak Budi",
    "role": "admin"
  }
}
```

JWT payload contains `tenant_id: 3` (decoded), tapi `user` object di response gak include. Frontend bisa decode JWT manually buat tau, tapi inconsistent dengan `POST /api/v1/tenant/register` yang return `user.tenant_id`.

**Production impact:** Cosmetic/inconsistency. Frontend AuthContext sudah ada custom decoding so tidak break.

**Recommendation:** Add `tenant_id` ke `user` object di login response. ~5 min fix.
